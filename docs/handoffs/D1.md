7 Oct 2026 · PR: opened by the orchestrator for branch `sb/D1` · model: Claude Opus 5.5 · sessions: decide (this one); a fresh-session review comes next

## What it does now

D1 is a decision session: it wrote documents, no code. It produced the inventory of every contract element the 86 PRDs use, and the list of every place they disagree, for D2 to decide with the user. Nothing in it is resolved.

Open first:
- `docs/contracts/CONFLICTS.md`: 118 entries (CF-001 to CF-118), an index with type and blocked sessions, and section 4, which maps the README's nine proposed decisions to the entries that contradict them. Sections: 1 topics and messages (CF-001 to CF-029), 2 tables, columns and storage (CF-030 to CF-059, with CF-059 the required list of tables named in one PRD only), 3 keys, jobs, values, budgets, flags, retention, rules and documents (CF-060 to CF-118, with CF-078 "job kinds no producer emits"; CF-118, the news article and URL keys, was added during verification).
- `docs/contracts/CONFLICTS-ASSUMPTIONS.md`: 113 entries (AU-001 to AU-113). About 770 assumptions one PRD makes about another service were each checked against that service's PRD; these are the ones it contradicts or does not support where a contract element depends on it. Entries that are the same disagreement are cross-referenced ("Same disagreement as"), and overlaps with CF entries are named where they were found ("CF overlaps").
- `docs/contracts/INVENTORY.md`: summary (topics, job kinds, tables at a glance), then by topic (producers, consumers, fields per PRD), by job queue (consumer, producers, kinds, fields, dead letters), by table (columns with writers and readers for Postgres, ClickHouse, object storage, Vault and other state), by budget tag, flags, retention classes, keys and identifiers, and a per-service index with each PRD's folder and build session.
- `docs/contracts/INVENTORY-VALUES-AND-CALLS.md`: the enumerations other services see and the internal calls between services (split out to keep INVENTORY.md readable).

## Run and test

No code and no tests. How the documents were built:
1. Extraction: one subagent per PRD folder (ten folders) plus one for `_shared` read every PRD in full and recorded each topic, queue and kind, table and column, budget tag, flag, retention class, key, enum and internal call with section and line, in JSON checked by a validator (all folders validated OK).
2. Merge: a script built the inventory from those files. This session read section 6 of all 86 PRDs by hand and checked the key formats, writers and job kinds behind the conflicts with `grep`; the extraction was also compared with the build plan's own index (`build-plan/tools/prd_io.json`), whose differences were its regex over-matching.
3. Conflicts: three consolidation subagents grouped the candidates by category and verified each against the PRD text; two audit subagents checked every cross-service assumption. Their scripts confirmed every `service §section Lline` reference falls inside the section it names.
4. Review: four fresh verification subagents then checked the conflict entries' references, claims and neutrality, and sampled inventory rows against the PRDs; their findings were fixed (see Review).

The working files (per-PRD JSON, scripts) stayed in the session scratchpad and are not part of the repository; the documents are the record.
