## Questions for the user

Numbered across the four apps, grouped by app, the ones that change most first. Each gives its source, the options with the recommendation first, and the consequences.

### All four apps

**Q1. Who builds the admin API and the admin console, and the n8n flows?** Source: the build plan has no session for them (`build-plan/SESSIONS.md`; only Q1, U1, U2, U3 are app sessions); F2's O-13; DEFERRED section 3 leaves the n8n flows to the orchestrator, I2 the nearest fit (ADR-0067). C7, C9, C12, X7 and others need the admin API's messages.

- (a) Recommended: a new session, U4 "Admin API and admin console", in wave 3 beside Q1, building the admin API first (C7's flag decisions, C9's review answers, X7's exports need it before G3) and the screens after; the n8n flows to I2. The flows move to their own PRD file, `docs/prds/apps/n8n-flows.md`, so each build session has one PRD.
- (b) The admin API inside Q1 and the screens inside U2. Fewer sessions, but Q1 and U2 grow by half, and U2 is in wave 5, late for the services that need the API.
- (c) Leave both until after G3; services keep testing against fakes. Nothing real answers a card or flips a flag before then.

**Q2. The hand-offs the contracts do not carry.** Source: ADR-0012 sends post refreshes to comment-decay-scheduler and backfill re-runs and X history to backfill-orchestrator, but F2 has no queue or kind from `admin-api` to either; people's deletion requests reach retention-purger's "deletion channel" (CONVENTIONS v1.1 L67) with no carrier; ops answers to other `review_queue` kinds (deletion-guard holds, `x_terms_screen`, `x_rule_flood`, `kb_candidate`, a news-dedup story split, `news-dedup §8 L123`), the `x_enterprise_required` acknowledgement (`quota-governor §5.3 L85`) and the canary's "pause a target, force a probe" (`source-health-canary §4 L35`) have none either.

- (a) Recommended: one proposal, written in round 2, adding request kinds produced only by `admin-api`: `client_refresh` on a new `jobs.comment-decay-scheduler`, `client_backfill` and `client_history` on a new `jobs.backfill-orchestrator`, `author_request` on a new `jobs.retention-purger`, and one `review_answer`-style kind per owning service for the review kinds above; applied by `/contract-change` (F2 is still in its fix round, so the cost is low now).
- (b) One control-plane table, `admin_requests`, written by the admin API and polled by each owner. No new queues, but polling, and each owner reads a shared table.
- (c) Synchronous HTTP endpoints on each owner. Simplest to call, but no replay, and every owner grows an API.

**Q3. Front-end technology.** Source: CONVENTIONS v1.1 L7 lists React and FlutterFlow in the stack; alert-evaluator names a "React app" for the rule editor (`§3 L27`).

- (a) Recommended: React with TypeScript (Vite) for the portal, dashboard and admin console, one shell and one sign-in, in this repository, tested with Vitest and Playwright.
- (b) FlutterFlow for the client-facing portal and dashboard, React for the admin console: faster screens, but two stacks, and the two-client isolation test is harder to run in CI.
- (c) FlutterFlow for all three.

**Q4. Interface languages.** Source: none; the clients are Iraqi brands and government bodies, the data Arabic, Sorani and English.

- (a) Recommended: Arabic (right to left) and English at launch, Sorani added after the pilot; every string in a translation file from the first screen.
- (b) Arabic, Sorani and English at launch: wider reach, one more translation and review pass before U1's screencast.
- (c) English first, Arabic later: fastest, but weak for clients and a later right-to-left rework.

**Q5. Users, roles and sign-in.** Source: "Portal users and roles are D3's" (ADR-0043); registry-writer already assumes roles `ops` and `client_admin` (`registry-writer §6.1 L88`); backfill-orchestrator lets only `client_admin` request re-runs (`§5.1 L50`).

- (a) Recommended: client roles `client_admin` (everything in the portal), `client_analyst` (reads and requests), `client_viewer` (reads); staff roles `account_manager` (assigned clients only), `ops`, `compliance_owner`, `admin`; Supabase Auth with email and password, TOTP required for every staff role and for `client_admin`; F3 adds the membership table (`client_members`) and the admin audit table (`admin_audit`) by proposal.
- (b) As (a) without `client_analyst`: simpler, but every requester must be an admin.
- (c) Single sign-on through each client's identity provider: needed by some government bodies, more work per client; could follow (a) later.

### Query API

**Q6. Do source views show every post of a watched source, or only keyword matches?** Source: aggregates and mentions are built on keyword hits only (`aggregator §5.3 A L53`, ADR-0031); a watched Page's posts that match no keyword produce no hit, yet the App Review slice must show "analytics on named Pages" (D3 brief, "Watch for"; U1 brief).

- (a) Recommended: source views read every post of a source in the client's `client_sources`, from `items_v` and `metrics_timeseries`, with query-api applying ADR-0053's visibility itself; keyword aggregates stay hit-based. Posts without a hit carry engagement but no sentiment, since analysis reads only hits (ADR-0031).
- (b) Only keyword matches everywhere: no new rule in query-api, but the App Review slice needs a keyword per Page and shows gaps.
- (c) A per-client "every post" keyword per watched source, so keyword-matcher hits every item: sentiment on all posts, but a contract change and more analysis cost.

**Q7. What government workspaces may see.** Source: alerts for government clients are aggregate-only, with no source name, handle or post link (`alert-evaluator §5.3 C L65`); CONVENTIONS v1.1 L251 forbids surveillance, sensitive-event monitoring and sensitive-attribute profiling; no PRD sets the views.

- (a) Recommended: aggregates and their breakdowns; item lists of registered organisations and media only (no individual's post or comment listed); public-account rankings of organisations only; no amber, no X before the gate opens.
- (b) Aggregates only, as their alerts: safest, but a ministry cannot read what its own outlets' coverage says.
- (c) The commercial views minus amber and X.

**Q8. YouTube figures across channel owners.** Source: no aggregation across channels of different owners except under the carve-out (CONVENTIONS v1.1 L355; ADR-0056); the carve-out is not defined in our documents.

- (a) Recommended, until counsel defines the carve-out: our own keyword mention counts may be summed across channels; YouTube's metrics (views, likes, comment counts) only per channel.
- (b) Nothing summed across owners, mention counts included: safest, but a keyword's YouTube total disappears.
- (c) Sum everything: a policy risk.

**Q9. Exports in v1.** Source: no PRD defines one; LinkedIn member data never exported (`li-own-comments-fetcher §7 L136`), Instagram output aggregated and de-identified only (`ig-account-media-poller §7 L135`).

- (a) Recommended: CSV of aggregates, and of item lists with id, time, platform, link, our labels, never text or author references; nothing for LinkedIn member content or Instagram third-party items.
- (b) Aggregates only.
- (c) Item text too where a platform's terms allow: more useful, a review per platform first.

**Q10. An API for clients' own systems in v1?** Source: none; alert webhooks already exist (`alert-evaluator §5.3 E L69`).

- (a) Recommended: not in v1; webhooks for alerts and deletions only.
- (b) Read-only API keys on the aggregate endpoints.

**Q11. Links to ordinary people's posts and comments.** Source: ADR-0010 forbids listing or ranking an ordinary person; a link to their own post or comment leads to their profile.

- (a) Recommended: show the text and a link to the post it sits under (or the registered source's post); never a link to an individual's own post, comment or profile.
- (b) Link everything: easier to verify, and every mention list then points at identifiable people.

**Q12. Several named saved lists per client?** Source: `client_lists` has a `list` type but no list name (CONVENTIONS v1.1 L84; ADR-0043 speaks of "saved lists").

- (a) Recommended: named lists, by a proposal adding `list_name` to `client_lists` before F3 runs.
- (b) One saved list per client, no contract change.

### Client portal

**Q17. Onboarding.** Source: DEFERRED section 3, "the client portal's onboarding screens" (owner D3).

- (a) Recommended: ops create the client, its contract settings and its first admin in the admin console; the admin then invites users and follows the checklist of `client-portal.md` 5.2 A.
- (b) Self-service sign-up with ops approval: faster for brands, but contract settings would wait in a pending state.

**Q18. Who sets `accepts_amber` and the flagged-vendor choice (Perplexity)?** Source: ADR-0052 (a) "set when the client's contract allows vendor data (D3 specifies the screen)"; `web-search-perplexity §1 L11` calls the Perplexity opt-out a client decision; `yt-web-search-bridge §4 L38` says client success configures it.

- (a) Recommended: ops, in the admin console, from the signed contract; the portal shows both read-only and links to the provenance statement.
- (b) The client admin in the portal, with the consent recorded: quicker, but a contract term set by a click.
- (c) The client asks in the portal, ops confirm.

**Q19. Which client requests exist in v1, and their limits.** Source: post comment refreshes beyond day 30 (CONVENTIONS v1.1 L171; eight PRDs), metrics refreshes (`fb-reactions-fetcher §3 L21`, `yt-video-details-fetcher §5.1 L45`), X history over a chosen window (`x-full-archive-search §3 L20`), backfill re-runs (`fb-backfill §14 Q3`, asked by D3).

- (a) Recommended: all four, by `client_admin` and `client_analyst`, within a per-client monthly cap ops set (ADR-0018 L52).
- (b) Post refreshes only in v1; the rest through the account manager.
- (c) None in v1.

**Q20. Clients and discovery.** Source: `qualifier §14 Q1` (client admins answering review cards), `§14 Q3` (queued candidates and their position), `fb-page-search §14 Q2` (a "never suggest again" control), all asked by D3.

- (a) Recommended: yes to all three. Client admins answer the review cards of candidates found by their own keywords, in the portal's review queue (ops still answer every card); queued candidates show with their queue position; "never suggest again" is kept per client in the qualifier's `client_settings` row.
- (b) Ops only answer cards; clients see queued candidates; no never-suggest control.
- (c) None of them.

**Q21. What disconnecting a property does.** Source: TikTok's terms require deletion on revocation (ADR-0054); the others say nothing (`ig-own-comments-fetcher §12 L173`).

- (a) Recommended: collection and push stop; data stays under its class until the client asks for deletion or offboards, except TikTok Display data, deleted at once (`authorization_revoked`).
- (b) Disconnecting deletes everything fetched under that grant.

**Q22. How a client proves it owns a YouTube channel.** Source: ADR-0066 lists YouTube channels as client-owned properties; nothing green needs a client token for YouTube.

- (a) Recommended: no OAuth; the client puts a code we give it in the channel description, ops confirm in the admin console, then the `add` is sent.
- (b) Google OAuth with `youtube.readonly`: automatic, but a sensitive scope and Google's app verification.

**Q23. How clients are told things.** Source: about twenty PRD lines say "the client is told" with no channel (missing grants, blocked sources, queued candidates, coverage paused, denied requests; see `admin-console.md` 5.3 C).

- (a) Recommended: a notification centre in the portal for every notice, plus email through n8n for the ones that need action (missing grant, blocked source, denied request); Telegram and Slack only for rule alerts, as the client chooses.
- (b) Email only.
- (c) The client chooses a channel per notice type.

**Q24. Telegram onboarding for channel owners who are not clients.** Source: "client staff or a cooperating outlet" (`tg-bot-channel-receiver §4 L33`).

- (a) Recommended: ops create a one-time onboarding link in the admin console for an outlet; the outlet needs no account; the channel joins the pool.
- (b) Client staff only in v1.

### Admin console

**Q25. How people's deletion requests come in.** Source: retention-purger's deletion channel is "an n8n intake form and a mailbox" (`§5.3 L78`, `§11 L148`); the admin console records the request and the confirmation (ADR-0069 (b)); Meta asks for a data deletion URL (approvals table).

- (a) Recommended: a public form on the company website and a mailbox, both landing in the admin console through n8n and the admin API; the confirmation to the account's public contact is sent and recorded there; the form's URL is the one given to Meta.
- (b) Mailbox only, entered by ops.

**Q26. Who curates logo sets, the knowledge base and taxonomies.** Source: `analysis-media §14 Q7` (logo sets, asked by D3; `brand_assets` is D3's writer, ADR-0025); `analysis-entities §4 L34` (clients add their brands and products); `analysis-topics §4 L38` (account managers and clients edit taxonomies).

- (a) Recommended: clients upload their logo sets and add their own brands, products and topics in the portal; an account manager approves each before it goes live; the global knowledge base and global taxonomy are kept by ops with the ML lead (A2 and A3 still ask their own §14 questions).
- (b) Only our staff write all of them.

**Q27. Which changes need the compliance owner, or a second person.** Source: none sets it; ADR-0068 and ADR-0069 give the register and `screened_terms` to "the user or the user's compliance owner".

- (a) Recommended: `permitted_uses` and `screened_terms` changed only by `compliance_owner`; offboarding, `legal` deletions and amber flag changes by ops with a second staff member confirming; everything else by one person; all audited.
- (b) Compliance-owner-only for the two tables, everything else one person.
- (c) No restrictions beyond the audit.

**Q28. Where Abdullah's reports live.** Source: cost and coverage reports several PRDs promise (`tg-message-search §4 L35`, `yt-keyword-search §4 L40`, `yt-web-search-bridge §4 L39`, `search-hit-router §4 L37`, `web-commoncrawl-scanner §4 L35`).

- (a) Recommended: a "Reports" section in the admin console, built after G2 with real numbers.
- (b) A weekly n8n email.
- (c) Later.
