# Plan · F2 Contracts package

Brief: build-plan/sessions/F2-contracts-package.md · PRD: none (foundation session; the requirements are the brief, CONVENTIONS v1.1 in full, the 55 ADRs that apply to F2, check 2 of G0 in `build-plan/GATES.md` and the definition of done in `build-plan/README.md`) · Approved by: the orchestrator, under the user's delegation (docs/orchestration/README.md), 25 Oct 2026

## Context the plan rests on

- **What was read, in the brief's order.** The brief; CONVENTIONS v1.1, the whole file; the 55 ADRs that apply to F2 (ADR-0001 to ADR-0014, ADR-0016 to ADR-0018, ADR-0020 to ADR-0027, ADR-0030 to ADR-0046, ADR-0051 to ADR-0054, ADR-0057, ADR-0059, ADR-0060, ADR-0064, ADR-0065, ADR-0067 to ADR-0070: 45 name F2 in "Applies to" or "Sessions that must read this", as `docs/handoffs/D2.md` L115 lists them, and ten more apply to "all"); `docs/decisions/DEFERRED.md`, whose rows name F2 nowhere (checked: no row names F2; the rows that touch an F2 shape are listed under "Contracts"); `docs/handoffs/D2.md` and `docs/handoffs/F1.md` (and `docs/handoffs/F1b.md`, for the contract guard on `sb/F2`); `docs/contracts/INVENTORY.md`, background only (ADR-0070); and the section 6.2 example of all 86 PRDs. ADR-0049, ADR-0050 and ADR-0066 were also read for the values of `lifecycle`, `push_covered`, the flags and the owned-property `add`, which `source.events` and `registry.decisions` carry. Subagents read the rest of the inventory and collected the closed value lists that ADRs ask F2 to fix without listing them; every list below cites its source.
- **Precedence.** An ADR wins over every PRD (ADR-0001), and where two PRD examples disagree the ADR decides, never a majority. Where no ADR touches a field, the producer's PRD 6.2 example stands, with ADR-0070's single spelling. INVENTORY and CONFLICTS are D1's record of the PRDs as written, background only (ADR-0070, CONVENTIONS v1.1 L5). Every PRD example below is read as its ADRs reshape it: flat routing fields fold into `provenance` (ADR-0003), the type is `kind` and never `reason` (ADR-0011), every id follows ADR-0006. Where an ADR asks F2 to close a list or declare fields and no ADR or PRD token gives a value, or the PRDs spell one value several ways, the plan drafts the value with its source and records Q8's approval of it (decided by the orchestrator on 25 Oct 2026); nothing is frozen on a guess.
- **What F2 builds.** `packages/contracts` v1.0.0: Zod 4 schemas for every topic, job and payload listed under "Contracts", exported as JSON Schema draft 2020-12 with Zod's own exporter, and Pydantic v2 models generated from those JSON Schemas (ADR-0030); the key and id helpers with TypeScript and Python twins and golden vectors (ADR-0006, ADR-0007, ADR-0009, ADR-0010, ADR-0035, ADR-0036, ADR-0044); the registries the SDK enforces (the producer table, ADR-0012; the partition-key record, ADR-0004; each producer's `context` keys, ADR-0005; each producer's visibility, ADR-0053); valid and invalid fixtures under `fixtures/contracts/`; conformance suites in both languages; `docs/contracts/VERSIONING.md` (ADR-0002).
- **What F2 does not build.** Tables (F3: `supabase/migrations`, `TABLE-OWNERS.md`), ClickHouse (F8), the SDK runtime that stamps, validates, partitions and enforces (F4, F6, F5), normalize-item's mappers (each producer's session with C4, ADR-0008), and the HTTP APIs of single services: quota-governor's request and answer and the SDK `report` (C1, F5), lang-dialect-id's call (C3), raw-archiver's replay, read and media endpoints (C2), the admin API's request endpoints and the client re-run and refresh endpoints of backfill-orchestrator and comment-decay-scheduler (D3, C10, C11). No ADR assigns those to F2, and `backfill-orchestrator §6.1` reads "the client re-run endpoint", an HTTP call. The one HTTP payload F2 types is n8n's (ADR-0067), which is also what clients' own alert webhooks receive: the same `n8n.alert/v1` message with `audience = client`, signed with the same helper (ADR-0067 L25, Q15), whether alert-evaluator posts it itself (alert-evaluator.md L69) or n8n delivers it.
- **Lane.** The work runs on `sb/F2`, which `.claude/hooks/guard-contracts.sh` lets write `packages/contracts` (F1b); the pull request carries the `contract-change` label, which the orchestrator applies (`docs/orchestration/README.md`). `packages/contracts` is a pnpm workspace through the `packages/*` glob, and a `pyproject.toml` in the same folder gets the Python steps of `make check`; Python consumers depend on it through `[tool.uv.sources] … = { path = "../../packages/contracts", editable = true }`; `fixtures/contracts/` needs no per-file README entry but is scanned for tokens (`docs/handoffs/F1.md`, "For the sessions that depend on this").
- **Who reads F2's handoff first.** F4 and F6 (they stamp, validate and enforce what F2 declares), F8 (column names follow the messages), G0 (check 2), then every service through the SDK.

### Message metadata and provenance (every topic)

- Every message: `schema` (`<topic>/v<n>`, a constant per schema; `dlq.<service>/v1` is the one pattern, F-52), `message_id`, `produced_at`, `producer {service, version, job_id}` (ADR-0002). `producer.job_id` is a ULID, never a composite or null (ADR-0006 L31), set as follows (F-17), in VERSIONING.md with a fixture per case: a job's own messages carry its `job_id`; a topic consumer copies its input's `producer.job_id` (ADR-0006 L31); a jobless receiver's record carries its receipt ULID; a job a scheduler emits carries that job's own `job_id`; a D3 writer's message carries the request's `request_id` ULID (see "Revision notes", R-3, for the portal's and console's writes); a time-driven loop's messages (alert-evaluator, source-health-canary) carry one ULID per evaluation run.
- Data messages (`raw.items`, `items.normalized`, `item.hits`, `discovery.hits`, `poster.profiles`, `item.metrics`, `items.analysis`, `article.urls`, `search.results`, `deletions`, `news.dedup`, `crawl.policies`, and `registry.decisions` that derive from a fetch) carry `provenance {route, vendor, service, fetched_at}` and a top-level `retention_class` (ADR-0003). `provenance.service` is the service that fetched; `producer.service` the one that emitted.
- Control messages (`job/v1`, `jobs.completed`, `source.events`) carry `producer` only and refuse `provenance` (ADR-0003).
- Exceptions: an author-, source- or client-scope `deletions` message carries the signal's provenance and no `retention_class`; when its signal is not a platform fetch (reasons `author_request`, `client_offboarding`, `client_request`, `legal`, `retention`), `provenance.route` and `provenance.vendor` are null, while `provenance.service` (the receiving service) and `fetched_at` (when the signal arrived) stay required (ADR-0003 L28 read for signals that involve no fetch, ADR-0070 L28; F-08, with a valid and an invalid fixture); a `registry.decisions` message entered by a person carries `requested_by` and no provenance (ADR-0003).
- Flat `route`, `vendor`, `service`, `fetched_at`, `item_fetched_at`, `found_at` as fetch time, `observed_at` as fetch time and `schema_version` in PRD examples give way to these fields (ADR-0002, ADR-0003).

### raw.items/v1

- Shape: one nested `{envelope, payload}` message for every producer; `payload` is the platform record as returned, minus identities, with `includes` and other response parts inside it; a news article is an extract by rule (ADR-0005, ADR-0010 L48). news-article-extractor's `article` payload is our own extract, not a platform record, so it is typed (F-30): `url`, `final_url`, `canonical_url`, `title`, `excerpt`, `published_at`, `text_full_ref`, `text_expires_at`, `text_sha256`, `title_sha256`, `extractor`, `extractor_version` (ADR-0070 L25 (h), whose spellings F2 takes, L40), plus the optional rest of news-article-extractor.md L109-L121; normalize-item and news-dedup read these fields (ADR-0031 L37, news-dedup.md L41).

- Optional declared route extras: `channel_id`, `live_state` (YouTube's `liveBroadcastContent`: `none`, `upcoming`, `live`, `yt-video-details-fetcher §5.1 L54`), `regressed`; `saves` inside `metrics` where the platform returns it (ADR-0034). `reactions_by_type` maps each reaction type the platform returns, in lower case on both items.normalized and item.metrics (Facebook `like`, `love`, `haha`, `wow`, `sad`, `angry`, `care`; normalize-item's upper-case `LIKE` example is rewritten), to its count, so its keys are platform data, not a closed list. `likes` is defined per platform; on Facebook it is the total of all reactions, so fb-reactions-fetcher's `reactions_total` maps to `likes` (normalize-item.md L114, fb-reactions-fetcher.md L118-L119; F2's choice, ADR-0034 L26 leaves it open; F-34, golden fixtures from both producers). `age_seconds` and `lateness_seconds` are derived by readers and not carried (ADR-0034).

Gone: `webhook_reconcile`, `refresh_24h`, `refresh_7d`, `refresh_client`, `plus_24h`, `24h`, `7d`, `item_idempotency_key`, `item_key`, `post_created_time`, `first_seen_at`, `due_at`, and the producers' `reactions_total` (as `likes` on Facebook, F-34), `call_id`, `baseline_missing` and `client_ids`, which ADR-0034's flat list leaves out (ADR-0034).
- Writers: normalize-item for reads whose records become items, labelled from `job_kind`; the reading service for count-only reads (ADR-0034, ADR-0024).

### deletions/v1

- Field set: the metadata, `deletion_id`, `reason`, `scope`, `mode`, `target`, `retention_class` (item scope only), `signal_at`, `due_at`; optional `requested_by`, `run_id`, `event_at`; the partition-key field once at the top: `source_id` (item and source scope), `author_ref` (author scope), `client_id` (client scope) (ADR-0035, ADR-0004, ADR-0003). `provenance`: the item's for item scope, the signal's for the other scopes (ADR-0003). Multi-item targets (F-07, F2's reading of ADR-0003 L28, in VERSIONING.md): the SDK deletion builder splits an item-scope target so that every message's items share the key, `platform`, `kind`, `provenance.route`, `provenance.vendor`, `provenance.service` and `retention_class`, and sets `provenance.fetched_at` to the newest `fetched_at` in the chunk; the split is deterministic (ids sorted, a fixed chunk size), so a repeated sweep emits the same messages and ids (`retention-purger §5.3 L72`). A multi-item fixture.
- `target`: `platform`, `kind`, `platform_ids`, `item_ids` (uuid v5 from the key helper, never ULIDs, ADR-0006), and the extras `fetched_before`, `countries`, `user_ids` (X: registered sources and every account a `poster_profiles` row holds, ADR-0010, ADR-0039); the subject of an author, source or client scope is the top-level key field (`author_ref`, `source_id`, `client_id`), never repeated in `target`, since key fields appear once, at the top (ADR-0035); an ordinary individual is targeted by `author_ref` only (ADR-0010, ADR-0035).
- Closed lists (ADR-0035, ADR-0054): `reason` `platform_sync`, `retention`, `author_request`, `client_offboarding`, `legal`, `authorization_revoked`, `client_request`; `scope` `item`, `author`, `source`, `client`; `mode` `delete`, `purge_text`, `purge_derived`, `withhold`.
- Gone from the PRD examples: `detected_at` (becomes `signal_at`), `emitted_at` (`produced_at` says it), `platform_status`, `x_job_id`, `parent_run_id`, `client_id: null` on item scope, the short form with only `idempotency_key`, scope `text_only` (yt-text-purger sends `item` with `purge_text`) and `derived` (`item` with `purge_derived`) (ADR-0035).
- `deletion_id` (Q2, decided by the user; F-01): `del:<reason>:<scope>:` followed by the 64 lower-case hex SHA-256 of the RFC 8785 canonical JSON of `{key, mode, signal_day, target}`. `key` is the scope's top-level key value (`author_ref`, `source_id` or `client_id`; for item scope, the item's `source_id`); every array in `target` is sorted; `signal_day` is the UTC date (`YYYY-MM-DD`) of `signal_at`, the day the signal arrived (the person's request, the client's offboarding or the platform's compliance signal, as each producer's PRD names it; for retention-purger's sweeps `signal_at` is the sweep's cut-off, so `signal_day` is its "cut-off day", `retention-purger §5.3 L72`, and a repeated sweep keeps its ids). This reads ADR-0035 L24's "whole sorted target" as including the subject key ADR-0035 itself moved to the top, plus the mode and the day, as the user chose. So every separate request is carried out (two clients' offboardings, two authors with equal targets, one author under two HMAC keys, a later request about the same subject, a `purge_text` then a `delete` of one item), and only an exact repeat of the same message keeps its id. A client-scope deletion carries `client_id` as its only key field and no `source_id` (ADR-0035 L24: "client scope `client_id`"). retention-purger's "one per affected `source_id`" (`retention-purger §5.3 L76`) therefore becomes one message per chunk whose target lists that source's `item_ids` and `platform_ids`, so the chunks' ids differ by target; a client-scope message with no item list is one per client and `signal_day` (F-01; see "Revision notes", R-1). Golden vectors cover each of those cases and a same-day replay; they are written only in this form (golden vectors never change inside a version).

  - a client alert, discriminated on a closed nine-value `rule_type` (ADR-0048 L42, L58-L65; F-22): `volume_spike`, `negative_share`, `new_high_reach_poster`, `keyword_first_seen`, `post_deleted_high_reach` (`alert-evaluator §5.3 L57-L61`), and four names drafted under Q8 for the types ADR-0048 names only in prose: `engagement_spike`, `topic_spike`, `entity_or_logo`, `story`. - The government rule (`alert-evaluator §6.2 L102`) applies to `subject` as well as `details` (F-50): a government client's alert carries no `subject.source_id`, no `subject.platform`, no `details.scope.source` and no `details.scope.platform`; an invalid fixture and a `validate()` check cover it.

A URL ops supply to li-org-resolver takes the existing `manual_candidate` path.

### job/v1 (every queue)

- Envelope: the metadata with `schema: "job/v1"`; `job_id` (ULID, deterministic where replay needs it), `kind`, `source_id` or the queue's declared key, `due_at`, `attempt`; for ops and client requests `request_id` and `requested_by`; optional `must_finish_by` on any job (ADR-0011, ADR-0002, ADR-0006, ADR-0057). Priority, route and vendor never travel in a job (ADR-0011, ADR-0018); `reason` is never the type and exists only as a declared kind field saying why a job was sent (ADR-0011). Control message: `producer`, no `provenance` (ADR-0003).
- `requested_by` names the actor: a service of the index (a news fetcher asking for a `recheck`) or the person the admin API records (D3 sets that reference's form).
- `post_ref` is the scheduler's object `{item_id, platform, platform_id, url}` on every queue, `url` optional; replies jobs add `thread_ids`, the parent comments' platform ids (ADR-0011, ADR-0060).
- Discriminated by `kind`; each kind's fields below. Where one kind serves several queues with different fields (`refresh`, `reconciliation`, `ops_force`), the producer table's row names the fields required on that queue, and both languages check the row.

### URL normalisation (ADR-0036; Q9, decided)

One function for every news finder, the extractor, the four search.results producers (web-search-perplexity, web-search-mojeek, web-gdelt-poller, yt-web-search-bridge, which compute `canonical_url_hash` with "the shared canonicaliser") and search-hit-router, which parks any message whose hash does not match (search-hit-router.md L57; F-45). ADR-0036 fixes the normaliser for `url_hash`; using it for `canonical_url_hash` and the `news:article` and `web:result` keys is F2's choice, consistent with ADR-0036 L24-L26. Parse as an absolute URL, resolving a relative one against the base the caller gives (`news-feed-poller §5.2 L55`); lower-case the scheme and the host, the host in its ASCII (punycode) form; drop the default port, the fragment, an empty query and the tracking parameters `utm_*`, `fbclid`, `gclid` (`news-feed-poller §5.2 L55`, `news-sitemap-poller §5.2 L59`); sort the remaining parameters by name then value, keeping repeats; percent-encode path and query as UTF-8 of NFC with uppercase hex, decoding unreserved characters (the "one form" `news-dedup §5.3 L64` gives Arabic slugs); keep the scheme, `www.` and a trailing slash, which can name different pages. `url_hash` is hex SHA-256 of the result's UTF-8. news-dedup's stricter story key (https, no `www.`, no trailing slash) stays inside news-dedup, and search-hit-router's platform matching rules (`m.`, `mobile.`, `twitter.com` read as `x.com`, `§5.3 L70`) stay its routing logic; neither is `url_hash`. Golden vectors come from the finders' and engines' examples, using their URL pairs only (`web-search-perplexity §6.2 L101-L102`: the `utm_source` parameter dropped; its truncated, prefixed hash at L103 is not a vector). yt-web-search-bridge's use of the function rests on ADR-0037 L24 (`canonical_url_hash` on all four producers' messages). Known limit: http/https and www/bare forms of one page hash differently; news-dedup's own key catches that for articles only (`news-dedup §5.3 L64`).

### query_key (ADR-0044; Q10)

The rule, decided by the user: on a platform whose own search treats Arabic spelling variants as the same, `query_key` treats them as the same search; on a platform whose search distinguishes them, each spelling stays a separate search. The mechanism, decided by the orchestrator: the package holds a per-platform folding profile (registry data, `registries/query-folding.json`) with two profiles, both with golden vectors: `exact` (Unicode NFC and lower case only) and `folded` (NFC, lower case, tashkeel and tatweel removed, alef forms أ إ آ merged to ا, ة to ه, ى to ي, and Persian ک and ی to Arabic ك and ي). `query_key` is hex SHA-256 of the RFC 8785 canonical JSON of `{"context_terms": [...], "forms": [...]}`, each array the texts as saved (handles keep `@`, hashtags keep `#`, `keyword-matcher §5.3 L56`), each text normalised under the row's platform profile, deduplicated and sorted by code point. Every platform starts at `exact`, which never merges two searches its platform would answer differently; a platform moves to `folded` only when its probe session records that its search treats those variants as the same, through a `/contract-change`, since the keys change (an open item per platform, under "Open items for the build"). Searchers still query every form of every keyword on a row (ADR-0044 L31), so neither profile loses coverage. Exclusions, `purpose`, `priority`, `platforms` and the client stay out (exclusions never enter a shared query, ADR-0044). The helper takes the two lists and the platform as arguments and calls no folding service, so identical saves give one key in both languages.
