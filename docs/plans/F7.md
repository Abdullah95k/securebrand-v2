## Fold specification v1 (what the code, the corpus and the reader follow)

The fold is a pure function of the text and its language label. It takes no other input.

```text
fold(text, lang) -> text_norm
```

There are two fold modes:

- **Sorani mode** for `ckb`: the Sorani fold applies to every token.
- **Arabic mode** for `ar`, `en`, `other`, `mixed` and `und`: the Arabic fold applies, except that a token holding a Sorani-only letter (ڕ U+0695, ڵ U+06B5, ۆ U+06C6, ێ U+06CE, ە U+06D5) takes the Sorani fold.

This is the PRD read literally (5.3 C: "the Sorani fold applies to `ckb` and to any token holding a Sorani-only letter"). It is also exactly normalize-item's fallback under `und` (PRD 8). `/v1/fold` accepts `ar`, `ckb` and `en` (5.3 D), so `en` is Arabic mode.

`text_norm` for a record is `fold(title)` and `fold(text)`, the non-empty ones joined by one space, title first.

The fold runs these steps in order. The table rows are the PRD's; the detail lines marked **D** are this plan's additions, approved as a set with edits E1 and E7 (Q3). The lines marked **E1** make the fold idempotent (D9): without them, deleting a mark, mapping a letter or case folding can bring together two code points that NFKC composes on a second fold.

Step 10, the token rules:

- **D3, URLs.** A URL starts at a position not preceded by a kept character. It begins `http://`, `https://` or `www.`, compared without case, and runs to the next White_Space character. It is matched on the text after step 1 and deleted whole. Bare domains (`zain.iq`) are not URLs: they become `zain iq`, and a keyword typed `zain.iq` folds the same way. This is the fold's own rule, defined on the NFKC'd text; extracting links into an array is normalize-item's (E5).
- **D4, kept characters.** These are the code points whose Unicode 15.1 general category is L*, M* or N*. The exceptions are variation selectors (U+FE00–U+FE0F, U+E0100–U+E01EF), the enclosing keycap marks U+20DD–U+20E4 and the emoji modifiers U+1F3FB–U+1F3FF, which become a space. Every other code point becomes one space: punctuation (، ؛ ؟ « » and ASCII), symbols, emoji, other format and control characters, and code points unassigned in 15.1. Character classes are those of 15.1, not the runtime's.
- **D5, hashtags and mentions.** `#` or `@` keeps its sign when it is not preceded by a kept character and is followed by at least one kept character or `_`. The token then runs over kept characters and `_`. Otherwise `#` and `@` become a space. `_` outside a hashtag or mention becomes a space. So `#البصرة_تنتفض` becomes `#البصره_تنتفض`, `#a#b` becomes `#a b`, and `x@example.com` becomes `x example com`. A `.` inside a handle becomes a space on both sides of the match: the PRD keeps only `@`, `#` and `_`.
- **D6, whitespace.** White_Space (15.1) collapses to one U+0020, and the result is trimmed.
- **D7, which tokens take the Sorani fold.** In Arabic mode, the token whose fold is chosen is a hashtag or mention (its sign, kept characters and `_`, as D5 reads them), or else a maximal run of kept characters. `_` joins tokens only inside a hashtag or a mention (E1), so `ڕ_ری` under `ar` is the two tokens `ڕ` and `ری` and folds to `ڕ ري`. Tokens are found on the text after row 2's second NFKC (E1). So NFKC has already mapped presentation forms to ۆ ێ and the rest, and composed ە ٔ into ۀ, which holds no Sorani-only letter. Row 0 (D-S1) belongs to Sorani mode only: in Arabic mode the ZWNJ is deleted before tokens are found, so a legacy ه + ZWNJ inside a Sorani token stays ه until `lang_rescore`, as PRD 8 accepts for the fallback.
- **D8, bad input.** A string holding a lone surrogate is refused with a `TextError` whose code is `not_unicode`, as F2's `validate()` refuses it. An empty or whitespace-only string folds to `""`. An emoji-only text folds to `""`, and keyword-matcher skips it (keyword-matcher 5.2 step 1).
- **D9, idempotence.** `fold(fold(x, l), l) == fold(x, l)` for every input, so a keyword or text folded twice is unchanged. The E1 lines make it hold, and a property test in both languages proves it (E1), under `ar` and under `ckb`: over every single code point; every pair of code points from the Arabic block U+0600–U+06FF (which holds the Sorani letters), Latin U+0020–U+007E and U+00A0–U+017F, the combining marks U+0300–U+036F and the format characters of row 1; and a seeded random set of strings drawn from Arabic and Sorani letters, the marks, Latin letters, `#`, `@`, `_`, URL prefixes and emoji. The critic's counterexamples are `unicode_edge` cases: U+0671 U+0654 under `ar`, U+0627 U+0640 U+0654 under `ckb`, U+00DF U+0307, and `ڕ_ری` under `ar`.
- **D10, the fold table is data.** `packages/text/data/fold-table.json` holds the maps and ranges, and the Python twin loads the same file. `FOLD_VERSION` is a token such as `fold-1`, and `FOLD_DATA_SHA256` is the hash of the fold table, F7's 15.1 data and `contracts`' unassigned ranges. **E7:** `data/fold-versions.json` is the version-to-hash history: for each released version, its `FOLD_DATA_SHA256` and the hash of the golden expectations (each case's `id`, `lang`, `title`, `text` and `text_norm`). `version.test.ts` and the twin's `test_version.py` fail when the data or the corpus differs from the current version's entry, and `version.test.ts` also pins every released entry, so a released version's hashes never change: a change is a new version with a new entry. C3 builds `FOLD_VERSION` into `lang_model_version` (lang-dialect-id 5.1, 13 item 12).
- **D11, the 15.1 data.** `data/unicode-15.1.json` holds the L, M and N ranges, White_Space and the case-folding map; the unassigned ranges are `contracts`' (Q6). It is generated by `scripts/gen_unicode_data.py`, which uses only the standard library, refuses to run unless `unicodedata.unidata_version == "15.1.0"`, and is run once by hand. It is committed, and a test regenerates it under uv's Python 3.13 and compares. **E7:** the test finds that interpreter with `uv python find` and sets `UV_PYTHON_DOWNLOADS=never`, so no test downloads anything; it is skipped with a message when none is installed, and CI has one.

Documented gaps, also in the README:

- Arabizi is never transliterated. It is case-folded Latin (ADR-0028).
- Kurmanji is folded like any `other` text.
- علي and على collide under the Arabic fold (PRD 12). Keyword exclusions handle that.
- In Arabic mode, a Sorani token without a Sorani-only letter takes the Arabic fold. Under `und` it stays wrong until `lang_rescore` (PRD 8). Example: `كوردستان وڵاتێکی جوانە`.
- In Arabic mode, a legacy ه + ZWNJ inside a Sorani token stays ه (D7).
- NFKC can compose a Sorani-only letter away: ە followed by U+0654 becomes ۀ (row 1 or row 2's second NFKC), recorded by a `unicode_edge` case (E6).

## Golden corpus `fixtures/text/golden.jsonl`

**Line format.** One JSON object per line, validated by `fixtures/text/golden.schema.json` (JSON Schema 2020-12):

```json
{"id": "iq-0001", "category": "iraqi_arabic", "lang": "ar", "title": null, "text": "النت منقطع بالبصرة من الصبح، شنو السالفة؟", "text_norm": "النت منقطع بالبصره من الصبح شنو السالفه", "rows": [4, 10], "anchor": true, "must_pass": true, "origin": "invented", "source": null, "reviewed": false, "note": "PRD 5.3 C example"}
```

Field values:

- `lang` is one of the six labels. Cases labelled `mixed`, `other` and `und` exercise Arabic mode.
- `rows` lists the table rows (numbers) and D-lines (strings such as `"D5"`, `"D-S1"`) the case exercises.
- `anchor` is true when the expected `text_norm` was written by hand, false when the Python twin computed it from the specification (E2).
- `origin` is `invented` or `public_domain`. A `public_domain` case names its work, author and year in `source`.
- `reviewed` turns true when the reader signs off the case.
- Every case is `must_pass`. A documented-gap case shows today's output and says so in `note`.

**Where the text comes from.**

- Every case is invented by the build session for this corpus: everyday sentences about services, weather, prices, football, traffic and telecoms, of the kind the platform listens to. None comes from a platform response, a fixture under `fixtures/<platform>/`, or anyone's post.
- Names are limited to:
  - public organisations and brands (Zain Iraq, Asiacell, Korek Telecom, ministries);
  - places (governorates and cities);
  - common given names used only as spelling examples (أحمد/احمد, as the PRD's 1 does).
- No private person is named. No handle other than a public organisation's or an invented one on a reserved pattern (`@example_*`) appears. URLs use reserved domains (`example.com`, `example.org`, RFC 2606) or a public organisation's home page. Phone-like digits stay in visibly fictional ranges (`0770 000 0000`).
- `public_domain` is allowed only for at most 20 lines of pre-1900 classical poetry: Arabic, for example al-Mutanabbi, and Sorani, for example Nali or Hajî Qadirî Koyî. Each names its source.
- `scripts/check-fixtures.sh` scans the folder for tokens (F1 L129). A corpus test checks the origin rules.

**How the expected values are written.**

1. First, before any code: at least 100 anchor cases (`anchor: true`) with hand-written `text_norm`, at least 5 for each PRD row 1 to 10 in each fold mode (E2). These include both PRD 6.2 examples, acceptance criterion 2's sentence in both spellings and every PRD row example.
2. Then the remaining cases. Their expected values are computed by the Python twin from the specification, never by the TypeScript fold, and diffed against the TypeScript fold before commit. A disagreement is resolved against the specification, never by copying one side (E2). The build reads each case again before commit.
3. Finally the reader reviews.

A golden vector never changes inside a `FOLD_VERSION` (the same rule as F2's golden vectors). A correction after merge is a new version.

**The reader** (the brief's "Your part"; the user arranges the reader; `docs/orchestration/README.md`, "What only the user can supply", the row "F7, C3"). The reader receives three files:

1. `fixtures/text/review/golden-review.csv`, generated from `golden.jsonl` by `scripts/review-sheet.ts` so the two never drift. It holds every case with Arabic script: about 430 rows, every category except pure English, URL-only and emoji-only cases. The columns are `id`, `category`, `lang`, input, expected `text_norm`, and a one-line English gloss of what the fold changed. The reader fills in `verdict` (`ok`, `expected wrong`, `unnatural`, `remove`), `corrected text_norm` and `comment`.
2. `fixtures/text/review/READER-GUIDE.md`, a one-page plain-language guide to the fold rules in English, with Arabic and Sorani examples. It says what to check: natural Iraqi and Sorani wording, that the expected output is right under each rule, and that nothing reads as a real person's words.
3. The specific rule questions for the reader, from Q1: ه + ZWNJ → ە, ھ → ه and ة → ە in Sorani; that KLPT's word-level standardisation stays out; and whether a common Iraqi or Sorani spelling variant is missing.

The reader returns the filled CSV, the answers to the rule questions, and a date. Their name is recorded only if the user wants it. F7 commits the returned sheet as `fixtures/text/review/golden-review-<date>.csv`, applies the corrections, sets `reviewed: true`, and records the outcome in `docs/handoffs/F7.md`. When the review happens relative to the merge is Q5.

## Revision notes

The orchestrator approved the plan on 25 Oct 2026, under the user's delegation, after an independent critic's check (no blocker, 7 should-fix items, 4 nits), with the edits E1 to E9 below. The build session applied them before writing any code.

- **E1 (idempotency).** Rows 2, 3 and 11 of the fold table gain the E1 lines: a second NFKC after the deletions, the deletion of U+0653–U+0655 after an ا, and a final NFKC. A final NFKC with the deletions alone, the critic's first suggestion, is not enough: U+0671 U+0654 folds to ا U+0654, the final NFKC makes it أ, and a second fold maps that to ا. The build session checked the three lines against Python 3.13's `unicodedata` before writing the plan: with all three, no single code point, none of the 501,264 pairs of D9's set and none of 200,000 seeded random strings, under `ar` or `ckb`, folds differently a second time; without the final NFKC 127 pairs do, without the alef line 24 do, and without the second NFKC strings such as ە ـ ٔ ی under `ar` do (the token loses its Sorani letter after the mode is chosen). D7: `_` joins tokens only inside a hashtag or a mention, and tokens are found after the second NFKC. D9 names the property test and its sets; `idempotence.test.ts` and `test_idempotence.py` join the uncovered behaviours. The critic's counterexamples join `unicode_edge`.
- **E2 (independent expected outputs).** "How the expected values are written": at least 100 hand-written anchors, at least 5 per PRD row 1 to 10 and fold mode, with `anchor: true`; every other expectation is computed by the Python twin from the specification and diffed against TypeScript before commit, a disagreement resolved against the specification. The line format gains `anchor`; acceptance row 1 gains the anchor count test.
- **E3 (missing labels).** Two categories join the corpus, `other` (12: Persian, PRD 13.4's Persian sentence among them for C3, and Latin-script Kurmanji) and `und` (12, with the Sorani-token override). The total becomes 554.
- **E4 (oversize text).** The uncovered behaviours gain the oversize row: a text of several megabytes folds in full, equals the fold of its chunks joined by one space, and finishes within 10 seconds (PRD 8).
- **E5 (scope).** `src/extract.ts`, its test and the extraction row are dropped; the ADR-0031 bullet, the consumers, D3 and the contracts table say that C4 extracts links, hashtags and mentions itself (normalize-item.md L75). The fold's own URL rule stays, defined on the NFKC'd text.
- **E6 (coverage wording).** The coverage rule covers rows 1 to 10 and D1 to D7 in each fold mode, and D-S1 and D-S2 in Sorani mode. The corpus test reads "at least 500 cases in all" with each category's planned count. The Sorani-letter test reads "survive the fold except where NFKC composes them", with a `unicode_edge` case for ە plus U+0654; the documented gaps say so.
- **E7 (version guard).** D10 gains `data/fold-versions.json`, the version-to-hash history over the fold data and the golden expectations, with `version.test.ts` pinning released entries; D11's regeneration test finds Python with `uv python find` and sets `UV_PYTHON_DOWNLOADS=never`; the reader's citation names the section and row of `docs/orchestration/README.md` instead of a line number. With Q6, D11's data no longer holds the unassigned ranges, which come from `contracts`.
- **E8 (dependencies).** The build outline's dependencies line states each dependency and its screen: no new one (`zod`, used for the corpus schema, is F2's screened row; the twin's tools are F1's), and any the build adds gets its row in the same pull request.
- **E9 (handoff for C3, C4 and F4).** The consumers line names C3's use of the twin; the handoff will state the fold's location (Q7), that C3's `/v1/fold` may use the Python twin, and that extraction stays with C4 (E5).
