## Fold specification v1 (what the code, the corpus and the reader follow)

The fold is a pure function of the text and its language label. It takes no other input.

```text
fold(text, lang) -> text_norm
```

There are two fold modes:

- **Sorani mode** for `ckb`: the Sorani fold applies to every token.
- **Arabic mode** for `ar`, `en`, `other`, `mixed` and `und`: the Arabic fold applies, except that a token holding a Sorani-only letter (ڕ U+0695, ڵ U+06B5, ۆ U+06C6, ێ U+06CE, ە U+06D5) takes the Sorani fold.

This is the PRD read literally (5.3 C: "the Sorani fold applies to `ckb` and to any token holding a Sorani-only letter"). It is also exactly normalize-item's fallback under `und` (PRD 8). `/v1/fold` accepts `ar`, `ckb` and `en` (5.3 D), so `en` is Arabic mode.

`text_norm` for a record is `fold(title)` and `fold(text)`, the non-empty ones joined by one space, title first.

The fold runs these steps in order. The table rows are the PRD's; the detail lines marked **D** are this plan's additions, and Q3 asks the orchestrator to approve them.

| # | Arabic fold | Sorani fold |
|---|---|---|
| 0 | none | **D-S1 (Q1):** ه U+0647 followed by U+200C (ZWNJ) becomes ە U+06D5, before step 1 deletes the ZWNJ. This is the legacy Persian-keyboard spelling of ە. |
| 1 | NFKC under Unicode 15.1 (by runs between 15.1-unassigned code points, as D-2). Then delete U+200B–U+200F, U+202A–U+202E, U+2066–U+2069, U+FEFF, and also **D1:** U+061C (Arabic letter mark) and U+2060–U+2064. | same |
| 2 | Delete U+064B–U+0652, U+0670, U+06D6–U+06ED and tatweel U+0640. **D2:** U+0653–U+0655 are not in the PRD's ranges and stay when NFKC did not compose them. | same |
| 3 | أ إ آ ٱ → ا | same |
| 4 | ة → ه | **Q1:** ة → ە (U+06D5), and **D-S2:** ھ U+06BE → ه U+0647. This explicit character table replaces "KLPT standardisation, pinned version". KLPT's word-level standardisation is not applied. |
| 5 | ک → ك | ك → ک |
| 6 | ى and ی → ي | ي and ى → ی |
| 7 | Kept as written: چ گ پ ڤ ژ ؤ ئ ء | Kept as written: ڕ ڵ ۆ ێ ە چ گ پ ڤ ژ ئ |
| 8 | ٠–٩ and ۰–۹ → 0–9 | same |
| 9 | **Q2:** full case folding under Unicode 15.1 (Python 3.13's `str.casefold`, generated as a table for TypeScript), applied to the whole text. Arabic script has no case. | same |
| 10 | Token rules, below. | same |

Step 10, the token rules:

- **D3, URLs.** A URL starts at a position not preceded by a kept character. It begins `http://`, `https://` or `www.`, compared without case, and runs to the next White_Space character. It is matched on the text after step 1 and deleted whole. Bare domains (`zain.iq`) are not URLs: they become `zain iq`, and a keyword typed `zain.iq` folds the same way. The extraction helper uses the same rule, so every URL the fold deletes is one `extractLinks` returns.
- **D4, kept characters.** These are the code points whose Unicode 15.1 general category is L*, M* or N*. The exceptions are variation selectors (U+FE00–U+FE0F, U+E0100–U+E01EF), the enclosing keycap marks U+20DD–U+20E4 and the emoji modifiers U+1F3FB–U+1F3FF, which become a space. Every other code point becomes one space: punctuation (، ؛ ؟ « » and ASCII), symbols, emoji, other format and control characters, and code points unassigned in 15.1. Character classes are those of 15.1, not the runtime's.
- **D5, hashtags and mentions.** `#` or `@` keeps its sign when it is not preceded by a kept character and is followed by at least one kept character or `_`. The token then runs over kept characters and `_`. Otherwise `#` and `@` become a space. `_` outside a hashtag or mention becomes a space. So `#البصرة_تنتفض` becomes `#البصره_تنتفض`, `#a#b` becomes `#a b`, and `x@example.com` becomes `x example com`. A `.` inside a handle becomes a space on both sides of the match: the PRD keeps only `@`, `#` and `_`.
- **D6, whitespace.** White_Space (15.1) collapses to one U+0020, and the result is trimmed.
- **D7, which tokens take the Sorani fold.** In Arabic mode, the token whose fold is chosen is a maximal run of kept characters, together with its hashtag or mention sign and `_`. It is found on the text after steps 1 and 2. So NFKC has already mapped presentation forms to ۆ ێ and the rest.
- **D8, bad input.** A string holding a lone surrogate is refused with a `TextError` whose code is `not_unicode`, as F2's `validate()` refuses it. An empty or whitespace-only string folds to `""`. An emoji-only text folds to `""`, and keyword-matcher skips it (keyword-matcher 5.2 step 1).
- **D9, idempotence.** `fold(fold(x, l), l) == fold(x, l)` for every case, so a keyword or text folded twice is unchanged.
- **D10, the fold table is data.** `packages/text/data/fold-table.json` holds the maps and ranges, and the Python side can load the same file. `FOLD_VERSION` is a token such as `fold-1`, and `FOLD_DATA_SHA256` is the hash of the table plus the 15.1 data. Changing either without bumping the version fails a test. C3 builds `FOLD_VERSION` into `lang_model_version` (lang-dialect-id 5.1, 13 item 12).
- **D11, the 15.1 data.** `data/unicode-15.1.json` holds the unassigned ranges, the kept ranges, White_Space and the case-folding map. It is generated by `scripts/gen_unicode_data.py`, which uses only the standard library, refuses to run unless `unicodedata.unidata_version == "15.1.0"`, and is run once by hand. It is committed, and a test regenerates it under uv's Python 3.13 and compares.

Documented gaps, also in the README:

- Arabizi is never transliterated. It is case-folded Latin (ADR-0028).
- Kurmanji is folded like any `other` text.
- علي and على collide under the Arabic fold (PRD 12). Keyword exclusions handle that.
- In Arabic mode, a Sorani token without a Sorani-only letter takes the Arabic fold. Under `und` it stays wrong until `lang_rescore` (PRD 8). Example: `كوردستان وڵاتێکی جوانە`.

## Golden corpus `fixtures/text/golden.jsonl`

**Line format.** One JSON object per line, validated by `fixtures/text/golden.schema.json` (JSON Schema 2020-12):

```json
{"id": "iq-0001", "category": "iraqi_arabic", "lang": "ar", "title": null, "text": "النت منقطع بالبصرة من الصبح، شنو السالفة؟", "text_norm": "النت منقطع بالبصره من الصبح شنو السالفه", "rows": [4, 10], "must_pass": true, "origin": "invented", "source": null, "reviewed": false, "note": "PRD 5.3 C example"}
```

Field values:

- `lang` is one of the six labels. Cases labelled `mixed`, `other` and `und` exercise Arabic mode.
- `rows` lists the table rows and D-lines the case exercises.
- `origin` is `invented` or `public_domain`. A `public_domain` case names its work, author and year in `source`.
- `reviewed` turns true when the reader signs off the case.
- Every case is `must_pass`. A documented-gap case shows today's output and says so in `note`.

**Count per category: 530 cases.**

| Category | Cases | What they cover |
|---|---|---|
| `iraqi_arabic` | 100 | Iraqi letters چ گ پ ڤ ژ kept; ک → ك; alef, taa marbuta and yaa variants; harakat and tatweel; colloquial spellings (شلون، هواية، اكو، ماكو، گاع); the PRD 6.2 Arabic example; علي/على collision |
| `msa` | 60 | Fully vowelled excerpts (harakat and U+0670 deleted), hamza carriers kept, ٱ wasla, news-style sentences with Arabic-Indic digits |
| `sorani` | 100 | At least 40 typed with Arabic ك ي ى ة or legacy ه + ZWNJ; the PRD 6.2 Sorani example; acceptance criterion 2's sentence in both spellings; every Sorani-only letter kept |
| `mixed` | 60 | 25 Arabic and English, including a brand name inside an Arabic sentence; 20 Sorani and English; 15 Arabic and Sorani in one text |
| `english` | 40 | Case folding, punctuation, apostrophes; at least 10 Arabizi (`shlonak`, `7abibi`), the documented gap |
| `emoji` | 30 | Emoji-only (folds to ""), ZWJ sequences, skin-tone modifiers, keycaps, flags, emoji glued to Arabic words |
| `urls` | 30 | http, https and www URLs inside Arabic and Sorani text; trailing Arabic punctuation; bare domains (not URLs) |

**Where the text comes from.**

- Every case is invented by the build session for this corpus: everyday sentences about services, weather, prices, football, traffic and telecoms, of the kind the platform listens to. None comes from a platform response, a fixture under `fixtures/<platform>/`, or anyone's post.
- Names are limited to:
  - public organisations and brands (Zain Iraq, Asiacell, Korek Telecom, ministries);
  - places (governorates and cities);
  - common given names used only as spelling examples (أحمد/احمد, as the PRD's 1 does).
- No private person is named. No handle other than a public organisation's or an invented one on a reserved pattern (`@example_*`) appears. URLs use reserved domains (`example.com`, `example.org`, RFC 2606) or a public organisation's home page. Phone-like digits stay in visibly fictional ranges (`0770 000 0000`).
- `public_domain` is allowed only for at most 20 lines of pre-1900 classical poetry: Arabic, for example al-Mutanabbi, and Sorani, for example Nali or Hajî Qadirî Koyî. Each names its source.
- `scripts/check-fixtures.sh` scans the folder for tokens (F1 L129). A corpus test checks the origin rules.

**How the expected values are written.**

1. First, before any code: 60 anchor cases with hand-written `text_norm`. These include both PRD 6.2 examples, acceptance criterion 2's sentence and every PRD row example.
2. Then the remaining cases, whose expected values are produced from the specification by the TypeScript fold (and, if Q4 is A, checked by the independent Python twin). The build reads each one again before commit.
3. Finally the reader reviews.

A golden vector never changes inside a `FOLD_VERSION` (the same rule as F2's golden vectors). A correction after merge is a new version.

**The reader** (the brief's "Your part"; the user arranges the reader; `docs/orchestration/README.md` L51). The reader receives three files:

1. `fixtures/text/review/golden-review.csv`, generated from `golden.jsonl` by `scripts/review-sheet.ts` so the two never drift. It holds every case with Arabic script: about 430 rows, every category except pure English, URL-only and emoji-only cases. The columns are `id`, `category`, `lang`, input, expected `text_norm`, and a one-line English gloss of what the fold changed. The reader fills in `verdict` (`ok`, `expected wrong`, `unnatural`, `remove`), `corrected text_norm` and `comment`.
2. `fixtures/text/review/READER-GUIDE.md`, a one-page plain-language guide to the fold rules in English, with Arabic and Sorani examples. It says what to check: natural Iraqi and Sorani wording, that the expected output is right under each rule, and that nothing reads as a real person's words.
3. The specific rule questions for the reader, from Q1: ه + ZWNJ → ە, ھ → ه and ة → ە in Sorani; that KLPT's word-level standardisation stays out; and whether a common Iraqi or Sorani spelling variant is missing.

The reader returns the filled CSV, the answers to the rule questions, and a date. Their name is recorded only if the user wants it. F7 commits the returned sheet as `fixtures/text/review/golden-review-<date>.csv`, applies the corrections, sets `reviewed: true`, and records the outcome in `docs/handoffs/F7.md`. When the review happens relative to the merge is Q5.
