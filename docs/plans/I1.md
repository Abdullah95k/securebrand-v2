# Plan · I1 Infrastructure (staging first)

Brief: build-plan/sessions/I1-infrastructure.md · PRD: none (an infra session; the requirements come from the brief, ADR-0027, ADR-0029, ADR-0054, ADR-0069, ADR-0039 and CONVENTIONS v1.1) · Approved by: pending (orchestrator)

## Scope and what this plan rests on

I1 builds staging as code under `infra/` and rehearses three procedures on it: a deploy, a rollback and a restore. That code covers the Hetzner servers, network and firewall; the k3s cluster; Redpanda; ClickHouse; the object-storage buckets with their lifecycle rules and the off-site B2 copy of `raw/`; TLS ingress for the webhooks; the image registry; the deploy pipeline; and backups. The production environment is written and checked, never applied, in I1 (Q3). Every apply is the user's, one approved step at a time (brief, "Your part").

Read for this plan:

- The brief.
- CONVENTIONS v1.1: Naming, repository, deployment (L15 to L101, including the object-storage prefix table at L87 to L98 and the analytics store at L100); Retention classes; Observability and SLOs; Security and compliance.
- ADRs that name I1: ADR-0027, ADR-0029, ADR-0054 and ADR-0069.
- ADRs that apply to "all": 0001, 0002, 0003, 0004, 0006, 0010, 0011, 0012, 0014, 0017, 0018, 0021, 0025, 0026, 0030, 0041, 0042, 0043, 0045, 0053, 0057 and 0070.
- The object-storage and Kafka ADRs: ADR-0039, ADR-0022, ADR-0016, ADR-0035, ADR-0047, ADR-0050, ADR-0056 and ADR-0067.
- `DEFERRED.md`, the rows that name I1. L32 holds the legal defaults of ADR-0069, for counsel before G4. L50 holds the Hetzner and Backblaze accounts, opened "when I1 starts".
- Handoffs: D2 (Needs first), plus F1 and F1b for the toolchain, CI, the GHCR mirror and the dependency check.
- F2's handoff and `docs/contracts/VERSIONING.md`, read-only from `origin/sb/F2` (PR #13, still in its fix round). I used them for the dual-publish window (at least 14 days), the dead-letter retention rule ("keep dead-letter topics' retention short") and the topic list.
- The receivers' PRDs, for the public endpoints. The ADR sweep and the endpoint list were done by subagents, which kept exact quotes.

Where an ADR overrides a PRD line, I name the ADR (ADR-0001):

- ADR-0039 removes `raw.replay`, so no such topic is created.
- ADR-0069 (d) settles `deletion-propagator §14 Q1` on backups: backups may outlive the deadline only if every restore re-applies the deletion log first.
- ADR-0027 makes the store "Hetzner Object Storage primary, B2 off-site copy", where `raw-archiver §11 L157` says "Backblaze B2 or Hetzner Object Storage".

Dependencies:

- D2 (merged).
- F1 and F1b (merged): toolchain, CI, the GHCR mirror, `docs/dependencies.md` and its check.
- F2, not yet merged: the topic and queue list and the partition-key registry (`registries`), from which I1 generates the topic manifests.
- F3 and F8, not yet built: the deploy pipeline's migration step runs their `supabase/migrations` and `clickhouse/migrations`. Until they merge, the rehearsals use an empty migration set and a smoke table in a scratch database.
- C2 (raw-archiver) and C13 (deletion-propagator): see Q6 and Q8.

## First apply, in order

The user approves each step. I1's build session prepares each command and checks its output. The user runs it, on their machine by default (Q2). Each step ends with a check, and nothing proceeds until the user says yes.

0. **Prerequisites (P1 to P6 below) exist.** The user exports the variables in their shell.
1. **`00-network`:** private network, subnet, firewall. `make infra-plan ENV=staging STACK=00-network`; the user reads the plan; `make infra-apply ...`; then a second plan shows no changes.
2. **`10-cluster`:** 1 control-plane server and 3 workers (sizes in `SIZING.md`), volumes, load balancer, k3s through cloud-init. Check: R1 (nodes Ready). The user fetches the kubeconfig over SSH from the admin IP.
3. **`20-storage`:** the Hetzner primary bucket (`sb-staging-data`) and backups bucket (`sb-staging-backups`), the B2 bucket (`sb-staging-raw-copy`), the lifecycle rules, and the bucket-scoped keys. Check: R4's lifecycle part.
4. **`30-dns`:** the zone or subzone and the records for `hooks.staging`. The user delegates the subzone at their registrar if they choose that option in Q7. Check: `dig`.
5. **Secrets into the cluster:** `secrets-apply.sh ENV=staging`. Check: secret names present, no values printed.
6. **Flux bootstrap:** the user adds the deploy key, then `flux bootstrap git --branch=main --path=infra/k8s/envs/staging`. Flux then installs CCM, CSI, Traefik, the operators, Redpanda, ClickHouse, the topics, the backups, the B2 copy and the ingress stub. Checks: R2, R3, R5 (Let's Encrypt staging, then production).
7. **Rehearsals:** R6 deploy, R7 rollback, R8 restore, R9 node drain, R4 B2 copy. Their evidence goes in the handoff.

Prerequisites the user creates before step 1:

- **P1. A Hetzner account and a Cloud project `securebrand-staging`,** and in it:
  - a read-and-write API token;
  - Object Storage enabled, with an S3 key pair;
  - the state bucket `sb-tofu-state` with versioning on. Versioning there is for state history; the state holds no platform data.
- **P2. A Backblaze B2 account** in the region of Q7, with an account-level key used only to create the bucket and its scoped key in step 3. It is revoked afterwards.
- **P3. A password manager entry for each secret above,** plus a new OpenTofu state passphrase.
- **P4. A domain for TLS,** at a registrar that is not Cloudflare, with DNS either delegated to Hetzner DNS or kept where it is (Q7).
- **P5. A supabase.com organisation and a staging project in Frankfurt (`eu-central-1`),** if Q1 is answered "hosted".
- **P6. A GitHub classic PAT with `read:packages` only, and the admin CIDRs** (the user's office or home addresses) for SSH and the k3s API.

## Sizing and price (summary; `infra/SIZING.md` holds the working)

Prices are approximate list prices. The build checks each one on Hetzner's, Backblaze's and Supabase's pages before step 1, and the user approves the total.

| Staging | Size | About per month |
|---|---|---|
| control plane | 1 × CX33 (4 vCPU, 8 GB) | EUR 6 |
| workers (apps, Traefik; one labelled `role=data` for Redpanda and ClickHouse) | 3 × CX43 (8 vCPU, 16 GB) | EUR 30 |
| volumes | ClickHouse 200 GB, Redpanda 100 GB | EUR 14 |
| load balancer | LB11 | EUR 6 |
| Hetzner Object Storage | base fee (includes 1 TB) | EUR 5 |
| Backblaze B2 copy | under 1 TB in staging | USD 1 to 7 |
| Supabase Pro (Q1) | 1 project | USD 25 |
| **Total** | | **about EUR 90 to 100** |

For production I size, not build. These are assumptions, to be replaced by store-writer's and raw-archiver's bytes measured in G2 (ADR-0029):

- **Volume:** 1,000,000 items a day.
- **Raw archive:** about 1 KB compressed per raw record, with archive-only kinds adding about 50%. That is about 0.55 TB a year, so about 4 to 5.5 TB at ten years once the shorter classes (YouTube 36 months, LinkedIn) are subtracted. The B2 copy is the same size.
- **Media under `media/`:** unknown until G2. At 100 KB per image on 20% of items it would be about 7 TB a year, which would dominate the cost. `permitted_uses` and retention bound it.
- **ClickHouse:** about 0.5 KB per row compressed, with analysis, metrics and aggregates on top, so about 3.5 TB per replica at ten years. That suggests tiered storage: recent partitions on volumes, older ones on an S3 disk in Hetzner Object Storage. This is a production decision before G4, not I1's.
- **Production machines:** a replicated ClickHouse pair (2 × CCX33) with Keeper on the 3 control-plane nodes; 3 Redpanda brokers (3 × CCX23, replication factor 3, `min.insync.replicas` 2); 4 to 6 × CX53 for the apps.
- **Production cost:** about EUR 600 to 900 a month in year one, rising with storage to about EUR 1,000 to 1,400 at ten years, media excluded.

| Secret leakage through plan output or state | encrypted state, sensitive outputs, wrapper scripts that never echo (A20) |

| Vendor drift: a new chart or image from a screened-out vendor | A13 |
| Shared-tooling edits break other lanes | minimal edits, each with its repo-checks test; `make check` and CI green before push |
| F2's topic registry changes after I1 merges | topics are generated from the registry; a test compares the manifest with the registry |
